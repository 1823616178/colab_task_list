## 1. TaskEvent 事件协议（核心）

Runner 与 Console 之间唯一的数据契约。`core.run_task()` 通过注入的
`emit()` 产出，CLI 模式下 `emit` 打印中文（保持 `start.sh` 可用），
服务模式下 `emit` 推 SSE 队列。

### 1.1 信封

```jsonc
{
  "v": 1,                                  // 协议版本，破坏性变更时 +1
  "task_id": "20260822-103102-c89fc79c",   // 见 §1.4
  "seq": 42,                               // 单任务内自增，从 0 开始，用于断线续订
  "ts": "2026-08-22T10:31:02.123Z",        // UTC ISO8601，毫秒
  "phase": "model.prepare",                // 见 §1.2
  "status": "progress",                    // start | progress | ok | warn | error
  "message": "下载 minimax_h3_fl2va...",    // 人类可读，可直接展示
  "data": {}                               // phase 相关载荷，见 §1.3
}
```

`status` 语义：

| 值 | 含义 | 是否入库 |
| :--- | :--- | :--- |
| `start` | 阶段开始 | ✅ |
| `progress` | 阶段内进度更新（高频） | ❌ 仅 SSE |
| `ok` | 阶段成功结束 | ✅ |
| `warn` | 非致命异常（如降级、重试） | ✅ |
| `error` | 阶段失败 | ✅ |

**入库规则**：`TaskEvent` 表只存 `start/ok/warn/error` 且非 SSE-only phase。
`progress`、`metrics.sample` 只走 SSE；`log.line` 只走 SSE 并落 `run.log`。
详见 [01 §4](./01-架构设计.md)。

## 2. Runner API（Python FastAPI）

- 监听 `127.0.0.1:8765`，**不暴露公网**
- 全部请求需 `X-Internal-Token: <shared-secret>`，否则 `401`
- 与浏览器 JWT 是**两套独立体系**

### 2.1 健康与自检

```http
GET /health
```
```jsonc
{
  "ok": true,
  "version": "0.1.0",
  "colab_cli_version": "0.6.0",   // requirements.txt 钉死，禁止 >=
  "transport": {
    "mode": "native",             // 实际通道：native | cli
    "requested": "native",
    "degraded": false,            // requested != mode 即为降级
    "probe": { "contents_client": true, "kernel_client": true }
  },
  "running_tasks": 1,
  "recovered_inflight": []        // Runner 重启后从 runner_state.json 恢复的对账项
}
```

> `transport.probe` 任一为 `false` → 自动降级 `cli` 并 `degraded: true`。
> Console 应在启动对账时读取，探测失败要在后台显式告警（见
> [01 §5 R1](./01-架构设计.md)）。

### 2.2 工作流

```http
GET  /workflows                    # 扫描 workflows/*.json
POST /workflows/{slug}/frames      # 包装 set_frames.py
```

`POST frames` 请求体：

```jsonc
{ "first": "/abs/uploaded/first.png",    // 可选
  "last":  "/abs/uploaded/last.png" }    // 可选
```

> 仓库根 `api.json`（minimax_h3）已接 `last_frame` → LoadImage 节点 122。
> 其他工作流若未接线，`last` 会被 `set_frames.py` 拒绝并透传 400。

### 2.3 任务

```http
POST   /tasks                      # 立即返回 task_id，后台执行
GET    /tasks/{id}                 # 状态快照
GET    /tasks/{id}/events?from_seq=0   # SSE，见 §2.5
POST   /tasks/{id}/cancel
POST   /tasks/{id}/redownload      # 包装 --download-only
GET    /tasks/{id}/output          # 返回本地绝对路径，不传文件体
```

`POST /tasks` 请求体（字段与 `run.py` 的 argparse 一一对应）：

```jsonc
{
  "workflow_config": "workflows/minimax_h3.json",
  "api_json": null,               // 覆盖配置中的 api_json，可空
  "session": "comfyui-h3",
  "accelerator": { "kind": "gpu", "spec": "A100" },
                                  // kind: gpu|tpu, spec: T4|L4|G4|H100|A100|v5e1|v6e1
  "mount_drive": true,
  "reuse": false,
  "keep": false,
  "input_dir": null,
  "workflow_overrides": {        // 仅允许 workflow editable_fields 声明的键
    "prompt": "本次任务的视频描述"
  },
  "timeout": 86400.0
}
```

响应 `202`：

```jsonc
{ "task_id": "20260822-103102-c89fc79c", "status": "queued" }
```

**并发约束**：同一 `session` 同时只能有一个非终态任务
（`ensure_reusable_session()` 遇 `Status: BUSY` 会直接退出）。
Runner 侧以 session 名为键做内存互斥，冲突返回 `409`。

### 2.3.1 ⚠️ api.json 必须快照，不能引用

`set_frames.py:98` `update_api_json()` 用 `os.replace()` **就地覆写**
`api.json`。现在是手动 CLI 步骤所以不易撞车；一旦上 Web，「设首尾帧」和
「提交任务」变成两个独立 HTTP 请求，**任务 A 上传时读到的 api.json
可能已被任务 B 的设帧操作改掉**。

规则：`POST /tasks` 受理时**立即快照**，之后一切引用快照：

```
colab_output/<task_id>/
├── api.json          ← 提交瞬间的快照；已应用 workflow_overrides，上传的是它
├── workflow.json     ← 工作流配置快照
├── inputs/           ← 素材硬链接（省空间，同盘）
├── events.jsonl      ← 见 §2.5
├── run.log
└── output.zip
```

副作用是好的：**历史任务从此可完整复现**，现在做不到。
任务级覆盖只写入该快照，不修改工作流共享的源 `api.json`。

### 2.3.2 ⚠️ 取消（cancel）语义

`kernel_client.execute_interactive` 在工作线程里阻塞，**Python 无法杀线程**。
所以「取消」只有两种真实手段，必须让用户明确选择：

```jsonc
POST /tasks/{id}/cancel
{ "mode": "interrupt" }   // colab restart-kernel -s <session>
                          //   VM 保留、模型仍在磁盘、可立即重投
                          //   远端可能已有部分产物，转 recoverable
{ "mode": "destroy" }     // colab stop -s <session>
                          //   VM 销毁、停止计费、产物全部丢失
```

- 默认 `interrupt`；`destroy` 前端必须二次确认并提示「产物会丢失」
- 处于 `queued`（尚未下发 Runner）→ 直接置 `canceled`，不碰 VM
- 取消后 Runner 仍需 `emit` 完整的 `task.canceled` 终态事件

### 2.5 SSE 事件流

```http
GET /tasks/{id}/events?from_seq=42
Accept: text/event-stream
```

```
id: 43
event: task
data: {"v":1,"task_id":"...","seq":43,"phase":"model.prepare",...}

: keepalive
```

- ⚠️ **事件必须落盘，不能只放内存。** Runner 每任务写
  `colab_output/<task_id>/events.jsonl`（每行一个事件，追加写 + fsync）。
  内存 ring buffer（2000 条）只是读取加速，`from_seq` 落在窗口外时**从文件读**。

  > 为什么必须：Nitro 若宕机 1 小时，2000 条 ring buffer 早已滚掉，
  > **终态事件丢失 → DB 永远停在 `running`**。任务跑 24 小时，
  > 这个窗口远远不够。

- `from_seq` 用于**断线续订**，语义是「返回 `seq > from_seq` 的全部事件」
- 每 15 秒发一次 `: keepalive` 注释行防中间层超时
- 任务终态后流关闭；已结束任务请求该端点则回放 `events.jsonl` 后立即关闭
- `metrics.sample` / `log.line` **不写 `events.jsonl`**（日志走 `run.log`），
  否则文件会爆 —— 见 §2.6

### 2.6 ⚠️ 远端日志量比预期大得多

`remote_workflow.py` 在 Colab 里跑，`sys.stdout.isatty()` 为 **False**，
所以 `ProgressDisplay._render()` 走的是**非交互分支**：

```python
if not self.interactive:
    if force or workflow_text != self._last_logged_workflow:
        print(workflow_text, flush=True)     # 每次变化打印一整行
```

`update_resource()` 同理，每次采样 `print(resource_text)`。
**ResourceMonitor 每 2 秒一次 → 24 小时 = 43200 行仅资源行**，
再叠加逐节点进度行。

三条对策：

1. `run.log` 硬上限 **64 MiB**，超过则滚动为 `run.log.1`（保留 1 份），
   并在事件流里 `emit(status="warn")` 提示已截断
2. 本地解析时，`ProgressDisplay` 的进度行**转成 `workflow.exec` 的
   `progress` 事件**而不是 `log.line`，且**按 1 秒节流**后再推 SSE
3. `update_resource` 的行解析成 `metrics.sample`，同样节流

> 好消息：非交互分支不输出 `\r`，所以 `OutputStreamReceiver.feed_stdout`
> (`run.py:154`) 的按 `\n` 切分不会出现无限缓冲。**改造时不要顺手把
> `interactive` 打开**，否则 ANSI 光标控制序列会污染事件流。

## 3. Console API（Nuxt / Nitro）

浏览器只与这一层通信。全部 `/api/**`（除 `auth/login`、`auth/refresh`）
须过 JWT 中间件。

### 3.1 认证

```http
POST /api/auth/login      { username, password } → { accessToken, user }
POST /api/auth/refresh                          → { accessToken }
POST /api/auth/logout                           → 撤销 refresh
GET  /api/auth/me                               → { user }
```

- `accessToken` 15 分钟，**只存 Pinia 内存**，不进 localStorage
- refresh token 7 天，`HttpOnly; Secure; SameSite=Strict` Cookie，
  哈希后存 `refresh_tokens` 表，支持撤销

### 3.2 业务

```http

POST   /api/workflows/:slug/frames      # multipart 上传首/尾帧

GET    /api/tasks?status=&page=&size=
POST   /api/tasks                       # 建 Task 行 → 转发 Runner
GET    /api/tasks/:id
GET    /api/tasks/:id/events            # SSE，转发 Runner 事件流
GET    /api/tasks/:id/log               # 下载 run.log
```

### 3.3 SSE 转发职责

Nitro 订阅 Runner 的事件流，**一份数据两个去向**：

1. 原样转发给浏览器（含 `metrics.sample` / `log.line`）
2. `start/ok/warn/error` 写入 `task_events` 表；终态时更新 `tasks` 行

浏览器断开不影响 Nitro↔Runner 的订阅 —— 后者必须持续到任务终态，
否则事件会丢。**Nitro 侧的订阅由任务生命周期驱动，不由 HTTP 连接驱动。**

### 3.4 错误响应

统一格式：

```jsonc
{ "error": { "code": "SESSION_BUSY",
             "message": "会话 comfyui-h3 仍有任务运行",
             "detail": {} } }
```

| code | HTTP | 场景 |
| :--- | :--- | :--- |
| `UNAUTHORIZED` | 401 | JWT 缺失/过期 |
| `FORBIDDEN` | 403 | 非 admin 访问用户管理 |
| `SESSION_BUSY` | 409 | 该 session 已有任务在跑 |
| `ACCELERATOR_UNSUPPORTED` | 400 | `validate_workflow_accelerator()` 拒绝 |
| `INPUT_NOT_FOUND` | 400 | `resolve_input_files()` 找不到素材 |
| `RUNNER_UNAVAILABLE` | 503 | Runner 未启动或健康检查失败 |
| `TRANSPORT_DEGRADED` | 200 + warn | 私有 API 探测失败，已降级（非错误）|
