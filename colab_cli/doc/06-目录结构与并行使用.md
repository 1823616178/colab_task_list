# 06 目录结构与并行使用

## 1. 原则：只新增，不移动

**整个 P0–P2 阶段，现有文件一个都不动。** 不是保守，是有三条硬约束：

### C1 · `api_json` 用了两种相对深度

`resolve_api_json()` (`run.py:951`) 相对**配置文件所在目录**解析：

| 配置 | `api_json` | 实际指向 |
| :--- | :--- | :--- |
| `workflows/minimax_h3.json` | `../../api.json` | `kaggle-code/api.json` ← **colab_cli 外面** |
| `workflows/inso_wan2_2_14.json` | `../flows/INSO_wan2_2_14.json` | `colab_cli/flows/` |
| `workflows/inso_wan2_2_14b_an2.json` | `../flows/INSO_wan2_2_14B_an2.json` | `colab_cli/flows/` |
| `workflows/inso_wan2_2_14b_an2_lora.json` | `../flows/INSO_wan2_2_14B_an2_lora.json` | `colab_cli/flows/` |

挪动 `workflows/` 或 `flows/` → 4 个配置同时失效。

### C2 · `SCRIPT_DIR` 锁死了三者的相对位置

`start.sh` 与 3 个 wrapper 都用 `SCRIPT_DIR` 定位：

```bash
export COLAB_WORKFLOW_CONFIG_PRESET="$SCRIPT_DIR/workflows/inso_wan2_2_14b_an2.json"
exec "$SCRIPT_DIR/start.sh"
...
run_args=( "$SCRIPT_DIR/run.py" --workflow-config "$workflow_config" ... )
```

`start.sh` / `run.py` / `workflows/` 必须保持现在的同级关系。

### C3 · `colab_output/` 有历史数据且路径硬编码

`run.py:20` `HERE = Path(__file__).resolve().parent`，输出写
`HERE / "colab_output" / task_id`。目录里已有 3 次任务结果。

    ├── run.py                                变薄壳，但路径/输出不变
    ├── remote_setup.py                       上传到 VM 执行，不动
    ├── remote_workflow.py                    上传到 VM 执行，不动
    ├── set_frames.py                         不动
    ├── workflows/  flows/                    不动（见 C1）
    ├── image/  video/                        输入素材
    ├── colab_output/                         历史结果
    ├── tests/

    │

### 为什么 `web/` 放在里面

Nuxt 侧与 Python 侧**只通过 HTTP 契约耦合**，没有任何相对路径依赖。
所以放哪都行 —— 放里面是为了现在方便（共享仓库、共享
`colab_output/`），将来要独立部署，一个 `git mv` 就能拆出去，
不会像 Python 那边一动就断。

`.gitignore` 补上：

```gitignore
web/node_modules/
web/.nuxt/
web/.output/
colab_output_dev/
runner_state.json
.env
```

### 各新增包的职责

| 目录 | 职责 | 依赖 |
| :--- | :--- | :--- |
| `contracts/` | 事件 JSON Schema，**Python 与 TS 的共同真相** | 无 |
| `colab_transport/` | 隔离 Colab 私有 API，可降级 | `google-colab-cli`（钉版本）|
| `colab_core/` | 编排逻辑，`emit` 注入，不认识 argparse/print | `colab_transport` |
| `colab_runner/` | FastAPI + TaskManager + SSE | `colab_core` |
| `web/` | Nuxt + TypeORM + MySQL | 只依赖 HTTP 契约 |

依赖是**单向**的：`web → colab_runner → colab_core → colab_transport`。
`run.py` 与 `colab_runner` 并列，都调 `colab_core`，互不感知。

## 3. 现在就能继续用

### 3.1 入口零变化

```bash
./start.sh                      # 照旧
./start_wan_animate_an2.sh      # 照旧
./stop.sh                       # 照旧
python run.py --gpu A100        # 照旧
```

P0.3 之后 `run.py` 只是薄壳，`emit` 实现为打印中文，**输出与现在逐字一致**
—— 这是 [P0 的验收标准](./05-任务清单.md)，不是「尽量」。

### 3.2 三层隔离

| 层 | 现有用法 | 开发用法 | 隔离手段 |
| :--- | :--- | :--- | :--- |
| 会话 | `comfyui-h3` | `dev-*` | 不同 session 名 |
| CLI 状态 | 默认 config | `/tmp/colab-dev.json` | `colab --config` |
| 输出 | `colab_output/` | `colab_output_dev/` | `COLAB_OUTPUT_DIR` 环境变量 |

**`--config` 隔离是必须的，不是可选的。** README §4.3 提到 CLI 用状态文件
维护会话名 → endpoint 的映射。开发时的 `colab new` 会覆盖你正在用的会话
映射，导致 `stop.sh` 找不到会话（就是 `stop_unmapped_endpoint()`
`run.py:64` 那个补丁在处理的场景）。

> ⚠️ **同样的竞争也存在于 Runner 内部**：并发跑两个不同 session 的任务时，
> 两个 `colab` 子进程会写同一个默认状态文件。Runner 必须**按 session 分配
> config 文件**：`colab --config <state_dir>/<session>.json`。
> 这是 [P0.2](./05-任务清单.md) 的一条。

开发侧统一：

```bash
export COLAB_CONFIG=/tmp/colab-dev.json
export COLAB_OUTPUT_DIR=$PWD/colab_output_dev
export COLAB_TRANSPORT=cli
```

> 需要给 `run.py` / `colab_core` 加 `COLAB_OUTPUT_DIR` 支持
> （默认回落到 `HERE / "colab_output"`），这是 P0.3 顺手做的小改动。

### 3.3 省钱提醒

你和开发同时跑 = **真的花两份计算单元**。开发期建议：

- 通路验证用 T4，别用 A100
- 优先用 `COLAB_TRANSPORT=cli` 跑通降级路径（本来就要验收）
- 给 `colab_core` 加 `dry_run` 模式：走完全部 emit 流程但不真的建 VM，
  用于调事件协议和前端 —— **这个投入产出比最高**，P1 前端联调全靠它
