# 01 架构设计

## 1. 现状与约束

现有代码 3092 行，本质是一个**三层 Colab 远程编排器**：

| 层 | 文件 | 行数 | 能否用 Node 重写 |
| :--- | :--- | ---: | :--- |
| 交互层 | `start.sh` / `stop.sh` / `set_frames.py` | 373 | ✅ 这次就是要换掉它 |
| 本地编排层 | `run.py` | 1348 | ❌ 依赖 `colab_cli` 包内部 API |
| 远端执行层 | `remote_setup.py` / `remote_workflow.py` | 1186 | ❌ 跑在 Colab 的 Python 内核里 |

两个硬约束，决定了 Python 必须保留：

1. **远端层物理上只能是 Python。** `remote_workflow.py` 是通过 `colab exec`
   发送到 Colab **Jupyter 内核**执行的，内核是 Python 内核。
2. **`run.py` 依赖 `google-colab-cli` 的内部 API**，不只是命令行。见
   `run.py:420` `colab_exec_workflow()`：

   ```python
   from colab_cli.runtime import ColabRuntime
   from colab_cli.contents import ContentsClient
   ...
   reply = runtime.kernel_client.execute_interactive(
       code, output_hook=handle_message, timeout=timeout_value)
   ```

   要在 Node 复刻，等于自己实现 Colab 私有 RPC + Jupyter ZMQ 协议 + ADC
   四 scope 认证。纯风险、零收益。

另有几条来自代码的业务约束，直接影响设计：

- **一个会话同时只能跑一个任务。** `run.py:1074` 检测到 `Status: BUSY`
  会直接 `sys.exit`。所以「任务队列」必须以 session 为并发单位。
- **任务可以跑 24 小时。** `--timeout` 默认 `86400.0`。
- **失败时会主动保留 VM。** `run.py:1330` 的 `finally`：取回失败时
  `keep_vm = True`，避免丢失远端成品。同时 `google-colab-cli` 自带独立
  保活守护进程 —— 这意味着**编排进程死掉，VM 仍在烧计算单元**。

## 2. 目标架构

Python 从「被调用的一次性脚本」升格为「有状态的作业服务」，
Nuxt 降级为纯展示与管理层。

```
┌────────────────────────────────────────────┐
│ 浏览器                                      │
│   Nuxt 3 · Pinia · SSE                     │
└──────────────┬─────────────────────────────┘
               │ HTTPS + JWT
┌──────────────┴─────────────────────────────┐
│ Nitro Server (colab-console)               │
│   · JWT 签发/校验、用户与鉴权               │
│   · TypeORM ── MySQL（唯一写入方）          │
│   · Runner 客户端 + SSE 转发                │
│   · 启动对账（孤儿 VM 检测）                 │
└──────────────┬─────────────────────────────┘
               │ HTTP 127.0.0.1:8765 + X-Internal-Token
┌──────────────┴─────────────────────────────┐
│ Python Runner (colab-runner, FastAPI)      │
│   · TaskManager（ThreadPoolExecutor）       │
│   · core.run_task(cfg, emit)               │
│   · colab_transport  native │ cli          │
│   · state.json（仅自身崩溃恢复）             │
└──────────────┬─────────────────────────────┘
               │ google-colab-cli
┌──────────────┴─────────────────────────────┐
│ Colab VM  ComfyUI + remote_workflow.py     │
└────────────────────────────────────────────┘
```

### 为什么不用 `child_process.spawn`

spawn 会让**任务生命周期绑死在 Node 进程上**。Nuxt 热更新、部署、崩溃时，
子进程要么被杀要么变孤儿，而它可能正卡在 `download_output_archive()`
(`run.py:888`) 的 16 MiB 分块重组中间，SHA-256 校验断在半路。

常驻服务把两者解耦：Nuxt 可以随便重启，任务照跑，重连后从
`?from_seq=N` 续订事件流。

## 3. 技术选型

| 组件 | 选型 | 说明 |
| :--- | :--- | :--- |
| 前端 | Nuxt 3 + TypeScript | SSR 不是重点，主要是 Nitro 一体化后端 |
| 状态 | Pinia | 见 [04-前端规范](./04-前端规范.md) |
| ORM | TypeORM | 实体即 schema 真相，`synchronize:false` + migration |
| 数据库 | MySQL 8 | 任务/会话/用户/模型缓存 |
| 认证 | JWT | access 15min（内存）+ refresh 7d（HttpOnly Cookie，存库可撤销）|
| 作业服务 | FastAPI + uvicorn | 单 worker + ThreadPoolExecutor |
| 缓存/队列 | **无** | 见 §4 |

## 4. 为什么不引入 Redis

Redis 的四个经典用途在本项目全部落空：

| 用途 | 本项目情况 | 结论 |
| :--- | :--- | :--- |
| Session 存储 | 用 JWT，本来就无状态 | 用不上 |
| 热数据缓存 | 热数据是 4 个 `workflows/*.json` + 几十行任务列表 | MySQL 秒回 |
| 分布式锁 | 单节点 Nitro；并发上限是 Colab 计算单元（实际 1–3 个 VM） | 内存 Map 足够 |
| pub/sub 队列 | SSE 与任务在同一 Python 进程内 | 直接队列转发 |

**本系统的瓶颈从来不是 QPS，是 Colab 那边 20 GB 模型下载和 24 小时超时。**

### 唯一有压力的地方：日志量

`remote_workflow.py` 的 `ResourceMonitor`（每秒采集）+ `ProgressDisplay`
（每 2 秒刷新）+ ComfyUI 输出，量很大 —— `run.py:25` 的
`COLAB_OUTPUT_TAIL_CHARS = 200_000` 就是被这个逼出来的。

**不用 Redis 的解法**（两步）：

1. **进行中**：Runner 内存 ring buffer（最近 2000 行）+ SSE 直推。
   `\r` 刷新的进度行就地覆盖，不落盘、不入库。
2. **结束后**：整段日志落 `colab_output/<task_id>/run.log`，
   `Task` 表只存路径。

因此 **`TaskEvent` 表存里程碑，不存日志行**（几十行/任务，不是几万行）。

### 何时才加 Redis

命中任意一条再加，**不要提前**：

- [ ] PM2 cluster / 多实例部署 → SSE 需要跨进程 fan-out
- [ ] 需要「立即登出」/ refresh token 批量撤销且量大 → 黑名单
- [ ] 真的要排队跑任务（提交 10 个让它自己跑） → 上 BullMQ（依赖 Redis）

## 5. 风险登记

### R1 · Colab 私有 API 断裂（最高）

`run.py:433` 覆写了上游**私有方法**：

```python
class TimedContentsClient(ContentsClient):
    def _request(self, method, path, params=None, json_data=None):
```

`google-colab-cli` 重构 `_request` 或 `ColabRuntime.kernel_client` 即失效。
**全项目 90% 的外部风险集中在 `colab_exec_workflow` 这一个函数里。**

**缓解：逃生通道已经存在，只是没接开关。**

| 路径 | 实现 | 依赖私有 API |
| :--- | :--- | :--- |
| `download_live_output_archive` (`run.py:839`) | `ContentsClient` | ⚠️ 是 |
| `download_output_archive` (`run.py:888`) | `subprocess ["colab","download"]` | ✅ 否 |
| `colab_exec_workflow` (`run.py:420`) | `ColabRuntime` | ⚠️ 是 |
| `colab_exec` (`run.py:583`) | `subprocess ["colab","exec"]` | ✅ 否 |

私有 API 只是「VM 未销毁时就开始下载」的**性能优化，不是功能刚需**。
全部退回公共 CLI 任务照跑，只是慢一点、少了实时流。

三条措施：

1. 抽 `colab_transport` adapter，`COLAB_TRANSPORT=native|cli` 可降级；
2. **启动自检**，探测 `ContentsClient._request` / `ColabRuntime.kernel_client`
   是否仍存在，失败立刻降级并告警 —— 避免「申请了 A100、跑了 20 分钟
   下载模型，取回结果时才炸」这种最贵的失败方式；
3. `requirements.txt` 钉死 `google-colab-cli==x.y.z`，**禁止 `>=`**。

### R2 · 孤儿 VM 烧计算单元（高，花钱）

Runner 崩溃/重启后，VM 因自带保活守护继续存活。

**缓解**：`Session` 表 + Nitro 启动对账 —— 拉 `GET /sessions` 与 DB 比对，
发现「DB 中无 running task 但 VM 仍活」则告警并提供一键停止。
顺带根治 `run.py:64` `stop_unmapped_endpoint()` 那个「本地名称映射丢失」补丁。

### R3 · 生态漂移（中）

`remote_workflow.py` 的 `prepare_models` / `prepare_custom_nodes` 依赖 HF
仓库路径与 ComfyUI 目录布局。变化可见、报错明确，且多数只需改
`workflows/*.json` 配置，不改代码。

### 维护面收敛

分离服务的真正价值：**契约锁住后，Colab 的变化被挡在 Python 服务边界内。**

```
colab-runner/    (Python, 独立版本号)   ← Colab 变了只动这里
   └─ 契约: TaskEvent JSON schema        ← 这个不变
colab-console/   (Nuxt/TypeORM/Pinia)   ← 一行不用改
```

Colab 相关的可维护面积从「通读 1348 行」缩到「adapter 约 30 行」。

## 6. 部署形态

同机部署最简单：

```
systemd: colab-runner.service   127.0.0.1:8765
systemd: colab-console.service  0.0.0.0:3000  (或 Nginx 反代)
共享目录: colab_output/         Runner 写，Console 读后 sendStream
```

**大 ZIP 不走 HTTP 中转** —— Runner 返回绝对路径，Nitro 直接
`sendStream` 给浏览器（输出包动辄几百 MB）。

Docker 需挂载两个 volume：`colab_output/` 和 `~/.config/gcloud`
（ADC 凭据，**不能打进镜像**）。

## 7. 安全基线

- Runner **只监听 `127.0.0.1`**，绝不暴露公网 —— 它能凭 ADC 创建 A100 VM，
  是直接花钱的接口。
- Runner 用 `X-Internal-Token`（共享密钥）鉴权，与浏览器侧 JWT
  **完全分开**两套体系。
- Nuxt 侧所有 `/api/tasks`、`/api/sessions` 路由必须过 JWT 中间件；
  用户管理限 `role=admin`。
